# Cherryngine — Philosophy

## Что это

Cherryngine — это движок для игровых серверов. Он не привязан к конкретной игре или протоколу. На нём можно строить режимы для Minecraft Java, Minecraft Bedrock, Hytale и любых других платформ одновременно.

Цель — дать разработчику режима инструмент где он пишет **геймплей**, а не инфраструктуру. Вся сложность спрятана в движке.

---

## Ключевые принципы

### Кроссплатформенность — фундамент движка

Любой функционал взаимодействия с клиентом оформляется через интерфейс. Например "отрисовать пули", "показать количество патронов", "переместить игрока" — это интерфейсы. Для каждой платформы пишется своя реализация. Игровая логика дёргает только интерфейс, не зная кто за ним стоит.

Это правило действует независимо от того, как написана игровая логика — через ECS, ООП, корутины или что-то ещё. Кроссплатформенность — свойство движка, а не конкретного подхода к написанию геймплея.

### Геймплей не знает про платформу

Игровая логика работает с абстракциями: `Player`, `PlayerOutputProvider`, кастомными интерфейсами режима. Она не знает отправляется ли пакет Minecraft Java клиенту, Bedrock клиенту или симулируется в тестах.

### ECS — один из способов писать геймплей, не единственный

`engine-ecs` — опциональный модуль. Движок не требует его использования. Можно строить игровую логику на обычных классах, сервисах, корутинах — лишь бы реализовывало `Tickable`.

В демо-проекте используется ECS потому что он хорошо подходит для игровой логики — явный порядок систем, data-driven компоненты, отсутствие скрытых зависимостей. Но это выбор разработчика режима, а не ограничение движка.

### Инстанс — единица изоляции

Инстанс — это изолированный игровой контекст (лобби, матч, арена, квартира). Инстансы полностью изолированы друг от друга: разные игровые состояния, разные физические пространства, разные игроки.

С точки зрения масштабирования, инстанс мог бы быть отдельным процессом или машиной. Однако несколько инстансов запускаются в одном JVM-процессе намеренно — чтобы шарить тяжёлые объекты (например, закэшированные чанки миров) и не держать по копии на каждый инстанс.

### Игрок намертво привязан к инстансу

`Player` — per-instance объект. Перевести игрока с одного инстанса на другой значит: уничтожить его в старом инстансе, создать заново в новом. Никакие Java-объекты между инстансами не передаются. Инстансы общаются только через роутер, передавая идентификатор игрока и `TransferData` (плоская карта данных).

Это позволяет в будущем прозрачно работать с инстансами на разных машинах (через Redis и т.п.) без изменения архитектуры.

### Сложное ядро — простые реализации

Вся сложность концентрируется в движке. Разработчик режима пишет простой код — геймплейные системы, интерфейсы, конфиги. Он не думает про сеть, сжатие, кэши чанков, физику terrain.

### Компоненты, а не события

Если тянет сделать event — нужно подумать, не лучше ли компонент + система. Events — не основной механизм коммуникации между системами. Это снижает скрытые зависимости и делает порядок выполнения явным.

### Движок vs проект на движке

В `engine-*` живёт только то, что применимо к любому режиму. Специфика конкретного режима (квартиры, оружие, матчи) живёт в `impl-*`. Когда геймплейная механика "дозревает" и доводится до блеска — она может мигрировать в движок.

### Нет ванильного Minecraft

Redstone, mob AI, генерация мира — не поддерживаются и не планируются. Режимы — это перенос других игр (CS, GTA, билд-баттл, RPG) или принципиально новые идеи.

## Антипаттерны

**Платформенный код в геймплейной логике**
```kotlin
class WeaponSystem {
    fun shoot(player: MinecraftPlayer) { // ❌ — конкретная платформа в геймплее
        player.connection.sendPacket(...)
    }
}
```

**Per-instance объект как @Singleton**
```kotlin
@Singleton class McEntityRegistry // ❌ — создаётся через InstanceScope/InstanceFactory
```

**Глобальный singleton с игровым состоянием**
```kotlin
object GlobalPlayerList { val players = mutableListOf<Player>() } // ❌
```

**Состояние между тиками в полях ECS системы**
```kotlin
class WeaponSystem : System() {
    private val cooldowns = mutableMapOf<EntityId, Long>() // ❌ — в компонент
}
```

**Логика в компонентах**
```kotlin
data class Health(var current: Int) {
    fun damage(amount: Int) { current -= amount } // ❌ — в систему
}
```

**Прямые ссылки между инстансами**
```kotlin
class Quest(val otherInstancePlayer: MinecraftPlayer) // ❌ — только UUID
```

**Реактивность через подписки**
```kotlin
healthComponent.onChange { updateUI(it) } // ❌ — через change detection в системе
```

## Границы ответственности

| Слой | Где живёт | Что знает |
|---|---|---|
| Игровая логика | `impl-*` | Интерфейсы движка, опционально ECS |
| Платформенные интерфейсы | `engine-core` или `impl-*` | Абстракции, не конкретные платформы |
| Платформенные реализации | `engine-minecraft`, `engine-bedrock`, `impl-*:minecraft` | Конкретный протокол |
| Общие кэши | `@Singleton` в DI | Данные без игрового состояния |
| Per-instance объекты | Создаются через `InstanceFactory` | Данные конкретного инстанса |
